# Architecture

A365 Capability Explorer is a static site: Vite, React, TypeScript (strict) and Fluent UI v9, hosted on GitHub Pages. There is no backend. Content lives in YAML, is validated at build time, and compiled to JSON that the app imports.

```
content/*.yaml, changelog.md ──► scripts/build-content.ts ──► src/generated/*.json ──► the app
                                  (Zod schemas + cross-reference checks, contentVersion)
```

## Content pipeline

- **Single definition of every type:** [`src/lib/content/schemas.ts`](../src/lib/content/schemas.ts) (Zod). Objects are strict, so a typo in a YAML key fails the build. The app imports the inferred types.
- **Validation:** `npm run content:build` parses each file, validates it against its schema, then runs the cross-reference checks in [`validate.ts`](../src/lib/content/validate.ts): duplicate ids, unknown source references, taxonomy files that match the typed ids, template placeholders, changelog references, orphaned sources and stale `lastVerified` dates (a warning after 90 days).
- **`contentVersion`:** the date of the newest changelog entry plus seven characters of a hash over every file in `content/`, with line endings normalized. It does not change on a rebuild, so saved assessments only look out of date when content changes.
- **Numbers are computed:** [`metrics.ts`](../src/lib/content/metrics.ts) computes every count. Site copy uses `{placeholders}`, and the build rejects a placeholder it does not know.
- **Source fidelity:** `source.featureText` and the availability flags are verbatim from the service description. [`source-snapshot.json`](../content/source-snapshot.json) keeps the raw published table, and tests compare it with the catalog after [normalization](../src/lib/content/normalize.ts) (NFKC, zero-width characters, curly quotes, non-breaking hyphens).

## App

| Folder            | What it holds                                                                 |
| ----------------- | ----------------------------------------------------------------------------- |
| `src/app`         | Route table, layout shell (header, footer, skip link, focus handling)         |
| `src/features`    | One folder per section. Pages are lazy route modules that export `Component`  |
| `src/components`  | Design-system components                                                      |
| `src/lib/content` | Schemas, validation, metrics, derived fields, templates, the typed accessor   |
| `src/lib/state`   | Browser storage and the Executive / Technical context                         |
| `src/lib/engine`  | Pure condition evaluation, label-based descriptions and deterministic mapping |
| `src/theme`       | Tokens, Fluent theme, base and print CSS                                      |
| `scripts`         | Content build, post-build, two-base-path build, Pages-like test server        |
| `e2e`             | Playwright and axe tests                                                      |

Only the landing page is in the main chunk. Every other page is a lazy chunk.

### Explorer and capability briefs

The explorer keeps `q`, `lens`, `group`, `view`, and repeated `compare` ids in the query string. Search replaces the current history entry; lens, view and comparison changes create history entries without resetting scroll. Invalid links show a warning, ignore unknown ids and limit comparisons to four distinct capabilities. Filtering covers all mapped layers and stages, including secondary entries. Matrix cells are textual and the table view remains available.

Capability briefs use the same catalog and source references, show verbatim service-description wording alongside editorial explanations, preserve differing source notes, and expose scope rules, risk associations and typical patterns. Unknown ids render the not-found page. Risk associations are editorial; pattern membership is generated by the engine using canonical answers and the neutral organization, never stored as capability metadata. A capability may map to no neutral pattern while still having organization-level rules.

### Mapping engine and patterns

[`evaluate.ts`](../src/lib/engine/evaluate.ts) is pure and receives validated content, separate organization/use-case answers and a content version. It rejects invalid inputs. Conditions use true/false/unknown logic: missing, empty and explicitly unknown answers do not become false under negation. Only true rules emit recommendations. Highest level wins while all reasons, rule ids, sources, evidence and scoped origins remain. The earliest explicit wave override wins, otherwise the catalog default applies. Results sort by pillar order, level and short name.

Outputs include in/out-of-scope capabilities and relevance conditions, anatomy, triggered and unknown risk themes, configured readiness checks, owner × lifecycle cells, per-agent decisions, integration paths, editorial Frontier associations, licensing counts with unknown eligibility/basis, intensity, GCC gaps and open questions. Ready means only configured gap conditions evaluated false, not deployment certification. Its percentage uses all configured checks, including unknowns; absent checks remain unknown outside the denominator. Potentially applicable global checks also remain unknown. Intensity is weighted planning density (3/2/1), normalized against all catalog capabilities; it is not a risk score.

The lazy pattern library generates its entire matrix through the same evaluator. Pattern briefs show neutral assumptions and read-only results. Samples merge visible overrides into their parent pattern via a `sample` query parameter; invalid combinations render not-found. Technical adds tables and illustrative what-if diffs. Customization links carry public pattern/sample ids to the diagnostic, never answers.

Questions, rules, patterns, risks, advisories, integration paths, Frontier associations, what-ifs, samples and golden scenarios are content data. [`validate-mapping.ts`](../src/lib/content/validate-mapping.ts) checks ids, source/capability/question/option references, scope/operator compatibility, answer shapes, coverage and scenario consistency. Every capability must have a rule and risk association. Golden tests assert authored Essential inclusions and complete exclusions for every pattern and sample; unsigned scenarios warn, not fail. The methodology route exposes the same data and clearly separates automated tests from SME signoff.

### Local diagnostic

The lazy `/diagnostic` layout provides a versioned local workspace with separate organization profiles and assessments referencing their organization by UUID. Schema checks reject duplicate ids, dangling references and unsupported storage versions. The storage adapter exposes failures, preserves corrupt raw data for recovery, keeps failed edits in memory and uses a saved-raw comparison for best-effort stale-tab detection. This is not a transactional multi-user database. A failed reset cannot unlock corrupt storage. Navigation and refresh warn about unsaved drafts.

Question types, bounds, section order, quick-scan membership, consultant notes and conditional visibility come from content. Quick/Full switching retains answers. Hidden unanswered questions do not enter the engine's open-question list. Pattern and sample starters seed only use-case answers, never the neutral organization. Shared organization edits intentionally update every linked mapping; profiles with linked assessments cannot be deleted.

Saved answer shape and compatibility with current content are checked separately: retired questions and options survive load for explicit recovery. Invalid answers block previews until corrected or explicitly cleared, without removing compatible fields. A content-version notice distinguishes current evaluation from the original save. The wizard reuses the mapping engine for a live anatomy, accessible table and planning preview; formal readouts, export/import and branding remain Phase 5.

### Understand and Learn

`personas.yaml` links roles to available explorer lenses or Learn anchors; validation rejects unknown anchors. `learn.yaml` holds the conceptual request flow, integration paths, product positioning and Frontier Firm phases. Separate `building-blocks.yaml`, `glossary.yaml` and `faq.yaml` files keep related concepts out of the capability count. Every learning claim carries source, evidence, review status and verification metadata; technical guidance has its own source reference. Unknown facts and summaries are `null` with `TODO(verify)` comments and render a visible pending-verification notice rather than an invented answer.

Learn is a lazy route with Executive/Technical depth, a bounded walkthrough and a full table alternative. It adds no browser storage or runtime external requests. A pure, per-render glossary matcher links only the first term or alias in annotated explanatory prose (Learn, overview pillar/phase explanations and capability briefs), preferring longer phrases and respecting word boundaries. Definitions, headings, navigation and verbatim source quotes are not rewritten. Glossary links work without hover; tooltips also support keyboard focus and Escape dismissal.

## Routing and hosting

- **The base path is never hard-coded.** Vite's `base` comes from `BASE_PATH`. The deploy workflow fills it from `actions/configure-pages` and falls back to `/<repo>` only when Pages reports nothing. The router `basename` and every link and asset use `import.meta.env.BASE_URL`.
- **Deep links:** `postbuild` copies `index.html` to `404.html`, so `/capabilities` loads on refresh. GitHub Pages serves that file with HTTP status 404, and the end-to-end server reproduces this exactly.
- **Both ways of serving are tested:** `npm run build:all` builds for `/` and for `/<repo>/`. CI and `npm run test:e2e` run the same tests against both.
- **`noindex`:** while `indexable` is false in `content/site.yaml`, every page carries a robots noindex tag. A `robots.txt` cannot do this on a project site, because it must sit at the domain root.
- **Workflows:** `ci.yml` runs on pull requests and is called by `deploy-pages.yml`, so a push to `main` is checked before it is published.

## State and privacy

No backend, cookies, analytics or runtime third-party requests (a Playwright test fails on any request to another origin). Browser storage goes through [`storage.ts`](../src/lib/state/storage.ts) under the prefix `cpcompass:`. Project sites under one `github.io` account share an origin, so the prefix is distinctive. A test keeps the Privacy page in step with what is stored.

The legacy prefix is retained after the rename so existing preferences and assessments remain available. Local storage keys are `cpcompass:depth` and `cpcompass:diagnostic`; React Router also uses session storage `react-router-scroll-positions`. Names and answers never enter assessment URLs, which contain only opaque UUIDs. Storage is not encrypted and can be read by people sharing the browser profile. Privacy discloses deletion behavior and the lack of backup/import until Phase 5.

## Design system

[`tokens.ts`](../src/theme/tokens.ts) feeds both the CSS variables (injected into `index.html` at build time) and the Fluent theme. A test fails on a raw color anywhere else, and another asserts the WCAG 2.2 AA contrast of every token pair. See the [design system](DESIGN-SYSTEM.md).

## Testing

- **CI browser environment:** verification uses the official version-matched Playwright container on an Ubuntu 24.04 host. Browsers and OS dependencies are preinstalled, avoiding deployment-blocking apt mirror downloads. A two-minute browser-launch check fails explicitly if the runtime is unusable; all browser and accessibility tests still gate deployment. Update the container tag with the locked Playwright version; a unit test keeps them aligned. The overall verification job remains capped at twenty minutes.

- **Public dependencies:** `npm run lockfile:check` checks locked package URLs without installing dependencies; CI runs it before `npm ci`. Upstream lockfile helpers also support offline URL repair, and unit tests enforce public URLs and integrity-checksum presence. No registry is configured in this repository. Registry URL repairs must preserve package versions and integrity hashes.

- **Vitest, `node` project:** schemas, validation, build script, tokens. **`dom` project:** the shell and pages, with Testing Library.
- **Playwright and axe:** deep links, assets, no third-party requests, `noindex`, keyboard and focus, zero axe violations in both views.
- The numbers in [`catalog.test.ts`](../src/lib/content/catalog.test.ts) are deliberate tripwires on the source-of-truth table. Update them in the same pull request as an intentional catalog change.

## Decisions and deviations from the build brief

The [build brief](A365-Navigator-Build-Brief.md) is kept as written. Where the build differs:

1. **Renamed** from "Agent 365 Navigator" through "Control Plane Compass" to **A365 Capability Explorer**. Read the old names in the brief as the current name. The repository and Pages base path now use `a365-capability-explorer`; the storage prefix is unchanged to preserve locally saved assessments and preferences.
2. **Hosting:** a public project site from a personal account. The brief's private pilot was not used: a private Pages site needs GitHub Enterprise Cloud. The site carries `noindex` until launch.
3. **Toolchain pins:** TypeScript 6.0 (typescript-eslint supports up to 6.0.x) and ESLint 9.39 (`eslint-plugin-jsx-a11y` does not support ESLint 10). Revisit when those plugins catch up. Dependabot is told to skip those updates, and major updates of `@types/node`, which follows the Node version in `.nvmrc`.
4. **`js-yaml` is a dev dependency.** It runs at build time only, so the browser receives compiled JSON.
5. **Contrast:** the brief's `#0078D4` is 4.27:1 on the paper canvas, below AA for text. Link text uses `#106EBE`, and form controls get their own border token (the hairline is decorative).
6. **`sourceNotes[].differs`** (an addition) marks a statement that differs from the service description, which drives "Sources differ, verify".
7. **Changelog `affects: [all]`** stands for the whole catalog. A bare `*` is a YAML alias, so it cannot be used.
8. **Orphaned sources fail content builds from Phase 3 onward.** The validator retains an explicit lenient option for fixtures. Hosting references are displayed separately on Methodology, not presented as capability evidence.
9. **Phase 4 diagnostic:** typed text, long-text, date, scale and choice inputs extend the Phase 3 rule questions. Assessments persist locally, while formal personalized readouts and exports remain Phase 5.
10. **Verification gaps:** the licensing FAQ (`lic-faq`) can still be read only in part. Unverified Learn answers are withheld and marked `TODO(verify)`; earlier catalog source-difference notes retain their existing warnings. The Work Trend Index phases were verified against the official article on 2026-10-24; these are organizational descriptions, not licensing tiers or deterministic access-model mappings.
11. **The lockfile resolves from the public npm registry.** The first lockfile was written through a private npm proxy and recorded that proxy's hostname for every package. It was regenerated with the same versions: each locked version was checked against the registry's published checksum, and every entry now carries a sha512 integrity. `npm run lockfile:check` and a unit test fail on any other registry, and `npm run lockfile:fix` rewrites the URLs offline. No registry is configured in the repo, so each machine keeps its own, and npm's `replace-registry-host` default lets a proxy serve the public URLs.
