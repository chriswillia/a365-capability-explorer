# Architecture

A365 Capability Explorer is a static site: Vite, React, TypeScript (strict) and Fluent UI v9, hosted on GitHub Pages. There is no backend. Content lives in YAML, is validated at build time, and compiled to JSON that the app imports.

```
content/*.yaml, changelog.md ──► scripts/build-content.ts ──► src/generated/*.json ──► the app
                                  (Zod schemas + cross-reference checks, contentVersion)
```

## Content pipeline

- **Single definition of every type:** [`src/lib/content/schemas.ts`](../src/lib/content/schemas.ts) (Zod). Objects are strict, so a typo in a YAML key fails the build. The app imports the inferred types.
- **Validation:** `npm run content:build` parses each file, validates it against its schema, then runs the cross-reference checks in [`validate.ts`](../src/lib/content/validate.ts): duplicate ids, unknown source references, taxonomy files that match the typed ids, template placeholders, changelog references, orphaned sources and stale `lastVerified` dates (a warning after 90 days).
- **`contentVersion`:** the date of the newest changelog entry plus seven characters of a hash over every file in `content/`, with line endings normalized. It does not change on a rebuild, so saved assessments only look out of date when content changes.
- **Numbers are computed:** [`metrics.ts`](../src/lib/content/metrics.ts) computes every count. Site copy uses `{placeholders}`, and the build rejects a placeholder it does not know.
- **Source fidelity:** `source.featureText` and the availability flags are verbatim from the service description. [`source-snapshot.json`](../content/source-snapshot.json) keeps the raw published table, and tests compare it with the catalog after [normalization](../src/lib/content/normalize.ts) (NFKC, zero-width characters, curly quotes, non-breaking hyphens).

## App

| Folder            | What it holds                                                                 |
| ----------------- | ----------------------------------------------------------------------------- |
| `src/app`         | Route table, layout shell (header, footer, skip link, focus handling)         |
| `src/features`    | One folder per section. Pages are lazy route modules that export `Component`  |
| `src/components`  | Design-system components                                                      |
| `src/lib/content` | Schemas, validation, metrics, derived fields, templates, the typed accessor   |
| `src/lib/state`   | Browser storage and the Executive / Technical context                         |
| `src/lib/engine`  | Pure condition evaluation, label-based descriptions and deterministic mapping |
| `src/theme`       | Tokens, Fluent theme, base and print CSS                                      |
| `scripts`         | Content build, post-build, two-base-path build, Pages-like test server        |
| `e2e`             | Playwright and axe tests                                                      |

Only the landing page is in the main chunk. Every other page is a lazy chunk.

### Explorer and capability briefs

The explorer keeps `q`, `pillar`, `console`, `licensing`, `gcc`, `setup`, `by`, `lens`, `group`, `view`, and repeated `compare` ids in the query string; defaults are left out of the URL. [`explorer.ts`](../src/features/explorer/explorer.ts) parses and writes that state and applies the filters, so the page only renders it. The requirement-area chips show faceted counts: each count is the result of every other active filter, so a chip never promises rows the list will not show. `by` groups the list by requirement area (the default), by product area or not at all; `lens` and `group` narrow the list by layer, lifecycle stage, risk or scenario, and links written for the earlier `lens=pillar` and `lens=console` still work. Search matches the catalog's wording, discovery questions and tags; when it finds nothing, whole-word `shortcuts` in `site.yaml` offer the filters a seller probably meant, each with its count. Search replaces the current history entry; filter, view and comparison changes create history entries without resetting scroll. Invalid links show a warning, ignore unknown ids and limit comparisons to four distinct capabilities. Filtering covers all mapped layers and stages, including secondary entries. Matrix cells are textual and the table view remains available. Home numbers link to the filters that count them, and a test checks that each link returns exactly its metric. Individual rows no longer repeat the draft marker: the list says once, with a computed count, that summaries are drafts, while briefs, readouts and prints keep the marker.

Capability briefs use the same catalog and source references, show verbatim service-description wording alongside editorial explanations, preserve differing source notes, and expose scope rules, risk associations and typical scenarios. Unknown ids render the not-found page. Risk associations are editorial; scenario membership is generated by the engine using canonical answers and the neutral customer, never stored as capability metadata. A capability may map to no neutral scenario while still having customer-level rules. The correction link opens a GitHub issue; a mailto link is shown only when `feedbackEmail` in `site.yaml` holds an address, and none is invented.

### Mapping engine and patterns

The code and the YAML files still call them patterns; the interface says "scenarios" and "customer" (where the code says organization). Route paths are unchanged.

[`evaluate.ts`](../src/lib/engine/evaluate.ts) is pure and receives validated content, separate organization/use-case answers and a content version. It rejects invalid inputs. Conditions use true/false/unknown logic: missing, empty and explicitly unknown answers do not become false under negation. Only true rules emit recommendations. Highest level wins while all reasons, rule ids, sources, evidence and scoped origins remain. The earliest explicit wave override wins, otherwise the catalog default applies. Results sort by pillar order, level and short name. [`pillars.ts`](../src/lib/engine/pillars.ts) groups a result by requirement area (`pillarRows`), lists the teams that own what is in scope (`peopleRows`), and derives which requirement areas each question can change (`questionPillars`) from the rules and readiness checks themselves, so the "Informs Security, Governance" note and the per-area coverage count never need hand tagging.

Outputs include in/out-of-scope capabilities and relevance conditions, anatomy, triggered and unknown risk themes, configured readiness checks, owner × lifecycle cells, per-agent decisions, integration paths, editorial Frontier associations, licensing counts with unknown eligibility/basis, intensity, GCC gaps and open questions. Ready means only configured gap conditions evaluated false, not deployment certification. Its percentage uses all configured checks, including unknowns; absent checks remain unknown outside the denominator. Potentially applicable global checks also remain unknown. Intensity is weighted planning density (3/2/1), normalized against all catalog capabilities; it is not a risk score.

The lazy pattern library generates its entire matrix through the same evaluator. Pattern briefs show neutral assumptions and read-only results. Samples merge visible overrides into their parent pattern via a `sample` query parameter; invalid combinations render not-found. Technical adds tables and illustrative what-if diffs. Customization links carry public pattern/sample ids to the diagnostic, never answers.

Questions, rules, patterns, risks, advisories, integration paths, Frontier associations, what-ifs, samples and golden scenarios are content data. [`validate-mapping.ts`](../src/lib/content/validate-mapping.ts) checks ids, source/capability/question/option references, scope/operator compatibility, answer shapes, coverage and scenario consistency. Every capability must have a rule and risk association. Golden tests assert authored Essential inclusions and complete exclusions for every pattern and sample; unsigned scenarios warn, not fail. The methodology route exposes the same data and clearly separates automated tests from SME signoff.

### Local diagnostic

The lazy `/diagnostic` layout provides a versioned local workspace with separate customer profiles (code: organizations) and assessments referencing their customer by UUID. Schema checks reject duplicate ids, dangling references and unsupported storage versions. The storage adapter exposes failures, preserves corrupt raw data for recovery, keeps failed edits in memory and uses a saved-raw comparison for best-effort stale-tab detection. This is not a transactional multi-user database. A failed reset cannot unlock corrupt storage. Navigation and refresh warn about unsaved drafts.

The assessment home is start-first: a customer name (or an existing customer), the cloud environment, an optional scenario and the question set, with the number of questions each set asks. A quick scan opens at the use case because the name and cloud were just given. Saved assessments, customer management and backup follow, the last two behind collapsed sections. Question types, bounds, section order, quick-scan membership, consultant notes and conditional visibility come from content, and every question has a plain-language `askPrompts` entry in `diagnostic.yaml` that the build requires. Quick/Full switching retains answers. Hidden unanswered questions do not enter the engine's open-question list. Scenario and sample starters seed only use-case answers, never the neutral customer. Shared customer edits intentionally update every linked mapping; profiles with linked assessments cannot be deleted.

Seeded answers are recorded as `assumedQuestionIds` on the assessment (every seeded answer except the use case name). The field is display only: the engine treats an assumed answer like any other. Confirming or editing an answer removes its id, and an assumption whose answer is later cleared stops counting. [`assumptions.ts`](../src/lib/state/assumptions.ts) holds both rules; the wizard, readout, canvas and exports mark what still stands as "assumed, not yet confirmed". The optional field extends workspace v1 without migrating old records.

The header's [customer shortcut](../src/app/CurrentCustomer.tsx) is a lazy chunk that only reads the saved workspace. It names the customer of the open assessment, canvas or readout (otherwise the most recently touched one), re-reads on navigation, on a `storage` event and when it opens, and links to that customer's use cases and to `/portfolio?customer=<id>`. It adds no storage key.

Saved answer shape and compatibility with current content are checked separately: retired questions and options survive load for explicit recovery. Invalid answers block previews until corrected or explicitly cleared, without removing compatible fields. A content-version notice distinguishes current evaluation from the original save. The wizard reuses the mapping engine for a live view of what applies in each requirement area (with a by-layer table alternative) and counts how many of the questions that can change each area are answered. The review step summarizes the result and links to the readout; it no longer repeats the in-scope table.

### Readouts and portable assessments

The lazy `/diagnostic/:id/readout` route shares the diagnostic provider, so autosave failures and unsaved-navigation protection still apply. `/canvas/:id` loads the same persisted workspace; `/canvas/blank` needs no storage and remains available during storage recovery. Both populated views reject incompatible answers before running the engine.

[`report.ts`](../src/lib/readout/report.ts) generates the readout from current content and separate organization/use-case answers. [`metrics.ts`](../src/lib/content/metrics.ts) computes the readout's summary and KPI counts. The UI reuses `MappingReport` for evidence and detail, adds a cover, anatomy and wave-based discussion roadmap, and keeps what-if deltas separate from the saved baseline. Markdown escapes user markup and includes answers, current content version, rule evidence, sources and the disclaimer. Clipboard and download failures are visible.

[`diagnostic-transfer.ts`](../src/lib/state/diagnostic-transfer.ts) defines a strict version-1 JSON envelope with a format discriminator, export time, current content version and validated workspace. A single-assessment export includes only that assessment and its organization. Imports are limited to 5 MiB, reject malformed/unsupported structures and broken relationships before confirmation, then append entities with fresh UUIDs while remapping organization references. Existing entities are never overwritten. Older answers and entity content versions survive for explicit correction; derived results are always recomputed, never trusted from a file. Import uses the normal storage adapter and conflict handling, including visible quota failures and in-memory drafts.

Readouts expose fourteen stable numbered exhibits in the order set by [`plan.ts`](../src/lib/readout/plan.ts), which the page, its contents list and the Markdown export all use: requirement areas, anatomy, risks, capabilities, decisions, people, readiness, operating model, integration, licensing, open questions, roadmap, frontier and what-ifs. Executive omits the five technical exhibits and Technical shows all of them plus a full appendix; each view is numbered 1, 2, 3… with no gaps, because a number is an exhibit's position in the plan for that view. The page shows a contents list beside the document, keeps print and PowerPoint in the toolbar with the other ways to share behind one menu, and lets the seller correct the engagement name, preparer and date inline. Scope labels accompany muted out-of-scope anatomy, which has a table alternative. Readiness percentages retain the engine's configured-check denominator and nullable unknown state. Markdown always contains the full technical readout regardless of the current depth toggle.

[`powerpoint.ts`](../src/lib/readout/powerpoint.ts) dynamically imports PptxGenJS only when exporting. Readouts contain exactly seven editable slides (title, requirement areas, summary, anatomy, risk controls, roadmap, licensing), canvases exactly one. Summary-length limits are explicit: complete detail and shortened answers are retained in speaker notes and the technical Markdown export, with a visible notice on every slide. Images are embedded data, never remote assets. Colors and Office-friendly fallback fonts derive from project tokens. OOXML tests check counts, XML validity, every declared/referenced part, notes, metadata and absence of external relationships; browser tests exercise actual downloads and local preview rendering. PptxGenJS is pinned to 4.0.0. Its multi-slide packages declare a nonexistent additional master part for every slide after the first, a defect also verified in 4.0.1 and 3.12.0. A narrow OpenXML normalization removes only those unused master declarations (any number of them, so adding a slide cannot break the export) after verifying every actual relationship and all other declared parts, and puts notes-master ids before slide ids as the Office schema specifies. Missing real content, referenced missing masters, external relationships or malformed XML fail explicitly; slide data and notes are never discarded. The previewer is development-only and never enters the deployed bundle. Targeted dependency overrides select patched image-size, ECharts and UUID versions; the export and rendering tests exercise their compatibility.

[`logo.ts`](../src/lib/state/logo.ts) accepts bounded PNG/JPEG uploads, checks dimensions before decoding and normalizes locally to a PNG up to 512 pixels per side and 512 KiB. The strict logo schema verifies matching dimensions, PNG structure and CRCs; SVG, animations and external URLs are rejected. An optional assessment field extends workspace v1 without injecting defaults into old records. Existing backups without logos still load unchanged; new logos survive duplication and copy-only JSON transfer. Older app versions do not understand this additive field. No new storage key is introduced; normal conflict/quota handling remains authoritative.

Canvas print styles use landscape layout. Both blank and dense, branded populated canvases are tested as one page on Letter and A4. Filled print views use explicit bounded summaries and retain full answers in the on-screen canvas, readout and Markdown; workshop prompts remain on the blank handout. Ten configured boxes, a requirement-area strip and the automatic control-point box form the canvas; the eleven-box contract counts the ten configured boxes plus the control-point box. Readout print events temporarily expand evidence details and every closed section on the page (the share menu and logo editor are `data-no-print`) and restore their previous state afterward. Named readout print pages reserve space for the running draft/version/disclaimer footer.

### Portfolios and workshops

The lazy `/portfolio` route (shown as "Compare use cases") uses the same diagnostic provider and storage protections and opens on the customer named in an optional `customer` query parameter. [`portfolio.ts`](../src/lib/portfolio/portfolio.ts) validates a distinct selection from a single customer, rejects incompatible answer sets with explicit per-assessment errors and recomputes all compatible results using the existing engine. Saved answers and versions are never rewritten. Selection and customer filters are component state only. Unknown business values are not plotted; expected-user bands set illustrative bubble areas without invented headcounts. The chart has a complete table alternative. Draft business-value/intensity cutoffs are validated content, and boundary tests cover all four quadrants.

Capability heatmap cells preserve each assessment's own recommendation level, and the rows are grouped by requirement area with the area in its own column. Shared foundations include only platform/both capabilities present in at least two selected assessments for that customer; their per-agent follow-up remains explicit. Readiness checks are grouped by stable check id while ready, gap and unknown cases stay separate. The combined percentage uses configured check counts, not an average of percentages. Licensing capability counts are deduplicated, access-model bases remain per case, and no user or license quantities are summed. Source differences, sovereign verification and unknown eligibility stay visible.

The existing JSON envelope supports a distinct selected-assessment list and includes only referenced customers. Import still assigns fresh ids, preserves original versions and answers, and uses the storage adapter's normal conflict/quota behavior. JSON export rejects selections exceeding the existing 5 MiB import limit so downloads remain importable; it adds no new format, storage key or backend.

The lazy `/workshop` route needs no diagnostic storage. [`workshop.yaml`](../content/workshop.yaml) supplies the draft facilitator guide, timed agenda, outputs, print labels and the checklist copy. Agenda duration is computed in `metrics.ts`. The requirements checklist has one table per requirement area, built from the catalog with write-in columns for the customer's requirement, owner and priority, and prints one area per page. Scenario and capability cards reuse the catalog and existing rule-condition renderer rather than maintaining a second mapping. Paired front/back blocks print on the same sheet; print buttons select the guide, the checklist or one card set synchronously before opening print, and `afterprint` restores the full screen view.

### Seller guidance

The lazy `/conversation` route is a guide for running a customer conversation. [`conversation.yaml`](../content/conversation.yaml) holds only editorial facilitation advice (the steps, labels and the note about myths still to verify) and states no product facts. Each requirement area's capabilities, discovery questions, owner teams and licensing and availability counts are computed from the catalog by [`conversation.ts`](../src/lib/content/conversation.ts), so the page cannot drift from it. Links in the content are checked against the pages of this site.

[`PresentationControls.tsx`](../src/components/PresentationControls.tsx) supplies non-persisting presentation mode on portfolios, workshops, readouts and canvases. It enlarges type and hides editing/navigation controls on screen only. Escape exits and returns focus to the toggle; unmount cleanup restores the normal shell. Printing remains independent of presentation mode. Browser tests cover both base paths, keyboard/focus cleanup, zero axe violations, selected transfer, responsive tables and real A4/Letter PDF outputs.

### Understand and Learn

`personas.yaml` links roles to available explorer lenses or Learn anchors; validation rejects unknown anchors. `learn.yaml` holds the conceptual request flow, integration paths, product positioning and Frontier Firm phases. Separate `building-blocks.yaml`, `glossary.yaml` and `faq.yaml` files keep related concepts out of the capability count. Every learning claim carries source, evidence, review status and verification metadata; technical guidance has its own source reference. Unknown facts and summaries are `null` with `TODO(verify)` comments and render a visible pending-verification notice rather than an invented answer.

Learn is a lazy route with Executive/Technical depth. Its sections follow the order of a customer conversation (positioning, myths and facts, the concept table, integration paths, building blocks, glossary) and the concepts are one table with their technical text in the same cell. It adds no browser storage or runtime external requests. A pure, per-render glossary matcher links only the first term or alias in annotated explanatory prose (Learn, overview pillar/phase explanations and capability briefs), preferring longer phrases and respecting word boundaries; because the first mention is the first one on the page, reordering sections changes where a definition tooltip appears. Definitions, headings, navigation and verbatim source quotes are not rewritten. Glossary links work without hover; tooltips also support keyboard focus and Escape dismissal.

## Routing and hosting

- **The base path is never hard-coded.** Vite's `base` comes from `BASE_PATH`. The deploy workflow fills it from `actions/configure-pages` and falls back to `/<repo>` only when Pages reports nothing. The router `basename` and every link and asset use `import.meta.env.BASE_URL`.
- **Deep links:** `postbuild` writes a copy of `index.html` named `<path>.html` for every page that has a fixed address, with that page's title and description. GitHub Pages serves `learn.html` at `/learn` with HTTP 200 and no redirect (checked against a live Pages site), so a shared link such as `/conversation` gets a preview that names the page and the browser keeps the page's history state. A folder of the same name would make Pages redirect to the folder, so pages addressed by an id (a capability brief, a scenario, a saved assessment) are not built this way. [`route-table.ts`](../src/app/route-table.ts) lists the pages, [`route-shells.ts`](../scripts/route-shells.ts) builds them, and a test keeps the table in step with the router. Every other address falls back to `404.html`, a copy of `index.html` that Pages serves with HTTP status 404 and that loads the same app. The end-to-end server reproduces both behaviors, including the rule that `/learn` is served from `learn.html` but `/learn/` is not.
- **Both ways of serving are tested:** `npm run build:all` builds for `/` and for `/<repo>/`. CI and `npm run test:e2e` run the same tests against both.
- **`noindex`:** while `indexable` is false in `content/site.yaml`, every page carries a robots noindex tag. A `robots.txt` cannot do this on a project site, because it must sit at the domain root.
- **Workflows:** `ci.yml` runs on pull requests and is called by `deploy-pages.yml`, so a push to `main` is checked before it is published.

## State and privacy

No backend, cookies, analytics or runtime third-party requests (a Playwright test fails on any request to another origin). Browser storage goes through [`storage.ts`](../src/lib/state/storage.ts) under the prefix `cpcompass:`. Project sites under one `github.io` account share an origin, so the prefix is distinctive. A test keeps the Privacy page in step with what is stored.

The legacy prefix is retained after the rename so existing preferences and assessments remain available. Local storage keys are `cpcompass:depth` and `cpcompass:diagnostic`; React Router also uses session storage `react-router-scroll-positions`. Names and answers never enter assessment URLs, which contain only opaque UUIDs; the comparison link's `customer` parameter is such an id too. Storage is not encrypted and can be read by people sharing the browser profile. Privacy discloses deletion behavior and the sensitive contents of exported files and copied summaries, and that the assessment record also notes which answers are still assumed. Import/export adds no storage keys or network requests.

## Design system

[`tokens.ts`](../src/theme/tokens.ts) feeds both the CSS variables (injected into `index.html` at build time) and the Fluent theme. A test fails on a raw color anywhere else, and another asserts the WCAG 2.2 AA contrast of every token pair. See the [design system](DESIGN-SYSTEM.md).

## Testing

- **CI browser environment:** verification uses the official version-matched Playwright container on an Ubuntu 24.04 host. Browsers and OS dependencies are preinstalled, avoiding deployment-blocking apt mirror downloads. A two-minute browser-launch check fails explicitly if the runtime is unusable; all browser and accessibility tests still gate deployment. Update the container tag with the locked Playwright version; a unit test keeps them aligned. The overall verification job remains capped at twenty minutes.

- **Public dependencies:** `npm run lockfile:check` checks locked package URLs without installing dependencies; CI runs it before `npm ci`. Upstream lockfile helpers also support offline URL repair, and unit tests enforce public URLs and integrity-checksum presence. No registry is configured in this repository. Registry URL repairs must preserve package versions and integrity hashes.

- **Vitest, `node` project:** schemas, validation, build script, tokens, the engine, report and PowerPoint generation, and the route shells. **`dom` project:** the shell and pages, with Testing Library. Route modules are imported at the top of a page test so the lazy chunk is warm before the first `findBy` query.
- **Playwright and axe:** deep links and their HTTP status, assets, no third-party requests, `noindex`, keyboard and focus, zero axe violations in both views.
- The numbers in [`catalog.test.ts`](../src/lib/content/catalog.test.ts) are deliberate tripwires on the source-of-truth table. Update them in the same pull request as an intentional catalog change.

## Decisions and deviations from the build brief

The [build brief](A365-Navigator-Build-Brief.md) is kept as written. Where the build differs:

1. **Renamed** from "Agent 365 Navigator" through "Control Plane Compass" to **A365 Capability Explorer**. Read the old names in the brief as the current name. The repository and Pages base path now use `a365-capability-explorer`; the storage prefix is unchanged to preserve locally saved assessments and preferences.
2. **Hosting:** a public project site from a personal account. The brief's private pilot was not used: a private Pages site needs GitHub Enterprise Cloud. The site carries `noindex` until launch.
3. **Toolchain pins:** TypeScript 6.0 (typescript-eslint supports up to 6.0.x) and ESLint 9.39 (`eslint-plugin-jsx-a11y` does not support ESLint 10). Revisit when those plugins catch up. Dependabot is told to skip those updates, and major updates of `@types/node`, which follows the Node version in `.nvmrc`.
4. **`js-yaml` is a dev dependency.** It runs at build time only, so the browser receives compiled JSON.
5. **Contrast:** the brief's `#0078D4` is 4.27:1 on the paper canvas, below AA for text. Link text uses `#106EBE`, and form controls get their own border token (the hairline is decorative).
6. **`sourceNotes[].differs`** (an addition) marks a statement that differs from the service description, which drives "Sources differ, verify".
7. **Changelog `affects: [all]`** stands for the whole catalog. A bare `*` is a YAML alias, so it cannot be used.
8. **Orphaned sources fail content builds from Phase 3 onward.** The validator retains an explicit lenient option for fixtures. Hosting references are displayed separately on Methodology, not presented as capability evidence.
9. **Phase 4 diagnostic:** typed text, long-text, date, scale and choice inputs extend the Phase 3 rule questions. Assessments persist locally and feed the Phase 5 readout and portable-assessment workflow.
10. **Verification gaps:** the licensing FAQ (`lic-faq`) can still be read only in part. Unverified Learn answers are withheld and marked `TODO(verify)`; earlier catalog source-difference notes retain their existing warnings. The Work Trend Index phases were verified against the official article on 2026-10-24; these are organizational descriptions, not licensing tiers or deterministic access-model mappings.
11. **The lockfile resolves from the public npm registry.** The first lockfile was written through a private npm proxy and recorded that proxy's hostname for every package. It was regenerated with the same versions: each locked version was checked against the registry's published checksum, and every entry now carries a sha512 integrity. `npm run lockfile:check` and a unit test fail on any other registry, and `npm run lockfile:fix` rewrites the URLs offline. No registry is configured in the repo, so each machine keeps its own, and npm's `replace-registry-host` default lets a proxy serve the public URLs.
12. **Seller-first names and structure.** After a review for sellers who guide customers through Agent 365, the interface says "scenario" (code: pattern), "customer" (organization), "product area" (console), "Assess" (diagnostic) and "Compare use cases" (portfolio), and the navigation follows the order of a conversation: Home, Learn, Capabilities, Scenarios, Assess, Compare, Workshop, with "How recommendations work" in the footer. Route paths, content ids and storage keys keep their old names so links and saved data keep working. Per-row "Pending SME review" markers were replaced by one computed summary on list pages, because a marker on every row stopped carrying information; briefs, readouts and prints still carry it. No feedback email address is shown until one is supplied.
